# Changelog

All notable changes to linuxcnc-grpc (the server and the Python, Go, Node.js and Rust clients) are listed here. Versions follow [semantic versioning](https://semver.org).

## Unreleased

Everything in this release is additive on the wire: 1.0 clients work with a 1.1 server, and 1.1 clients work with a 1.0 server apart from the new RPCs and fields. The server now refuses some command values it used to pass on, lists only the machine's own joints and spindles in the status, and reports several HAL fields differently; see Upgrade notes. The package version is the API version; the protos carry no version of their own and the `linuxcnc` and `hal` package names are unchanged.

### Added
- **`CommandResponse.linuxcnc_serial`.** `SendCommand` now also returns LinuxCNC's own serial for the command. It identifies the command LinuxCNC was given, and can be compared with `task.echo_serial_number` or passed to `WaitComplete`. LinuxCNC's send normally returns once the task has echoed the serial, but it gives up after about 5 seconds without an error if the task does not answer, so a set value is not proof the command was received: confirm that, and the outcome, with `WaitComplete` or the status. If LinuxCNC's command serial did not change across the send, LinuxCNC did not take the command (its bindings report no error when the write to the command channel fails): the answer is then `RCS_ERROR` with no `linuxcnc_serial`. `CommandResponse.serial` and `RCS_DONE` ("dispatched") keep their 1.0 meaning.
- **`WaitCompleteRequest.linuxcnc_serial`.** Set it to the value `SendCommand` returned to wait on that command's serial instead of the latest one sent through the server. The wait follows LinuxCNC's own serial rule, so it is exact as long as nothing else is sent to LinuxCNC meanwhile: once a later command has been echoed, from this server or any other client, the answer is `RCS_DONE` and does not say how the earlier command ended. Read the status as well to know that a motion has finished. The serial has to be one this server issued on its current connection to LinuxCNC; anything else gets `RCS_ERROR`. Left unset, `WaitComplete` behaves as before.
- **`ReadFile` RPC.** Downloads a file from the NC files directory, with the same path rules as `UploadFile` and `DeleteFile`. Content is returned as bytes in chunks of up to 1 MiB (`offset`, `max_bytes`, `end_of_file`), so every response fits a client's default receive limit. If the file's size or modification time changes while a chunk is being read, the call fails with `ABORTED` and the client should start again from offset 0. Only regular files are read; the file is opened without blocking and without following a symbolic link at the file itself, so a FIFO or a link put in its place after the name was checked is refused rather than hanging the call or being followed. The other file RPCs in that case: `UploadFile` does not follow the link either, `DeleteFile` removes the link rather than its target, and `ListFiles` follows a link put in place of the directory it lists. No file RPC guards against a local user changing the directories above the file. The Go client gains a `ReadFile` helper that reads a whole file.
- **`ResolveFile` RPC.** Returns the canonical path a name resolves to, whether it goes through a symbolic link, and whether it is the program LinuxCNC has loaded (`is_loaded_program`, `loaded_program`, `interp_state`). Clients can now tell whether replacing or deleting a file would touch the loaded program.
- **`GetMachineConfig` RPC.** Returns what clients previously had to guess: the kinematics module and type, coordinates, which axis each joint drives (for `trivkins`, including gantries and lathes; extra joints set with `num_extrajoints` are listed without an axis letter, since they drive none), per-joint and per-axis limits, velocities and accelerations, home sequences, linear and angular units, and lathe and override hints from the INI file. An INI integer outside the int32 range is left unset and an INI number that is not finite (`nan`, `inf`, `1e999`) is reported as 0, each with a warning in the server log. The Go client gains a `GetMachineConfig` helper.
- **`GetServerInfo` RPC.** Returns the server's version (`server_version`, the linuxcnc-grpc package version), whether the server is connected to LinuxCNC (`linuxcnc_connected`) and LinuxCNC's version (`linuxcnc_version`, empty if not known). It answers while the server is waiting for LinuxCNC, and it never waits behind a command: it does not ask LinuxCNC anything. A 1.0 server answers `UNIMPLEMENTED`, so a client can use this RPC to tell a 1.0 server from a later one before it relies on anything added since. The Go client gains a `GetServerInfo` helper.
- **Error messages are fanned out to every client.** One reader in the server now reads LinuxCNC's error channel and hands each message to every `StreamErrors` subscriber. Concurrent streams used to split the messages between them. The server keeps the newest 256 messages; a subscriber that falls further behind than that loses the older ones without an error, which shows only as a jump in `ErrorMessage.sequence`.
- **`LinuxCNCStatus.errors` is filled in.** It carries the newest 20 messages the server has read, with type, timestamp and sequence. It was always empty before.
- **`ErrorMessage.sequence`**, a per-server counter that is the same for a message in the stream, in `status.errors` and in a replay, so clients can drop duplicates and notice gaps.
- **`StreamErrorsRequest.replay_buffered`** starts a stream with the messages the server already holds (up to 256).
- **`--error-channel on-demand|always|off`** chooses when the server reads the error channel. Reading it takes messages away from the machine's GUI, and no setting can avoid that: LinuxCNC's error channel is a single queue with no way to look without taking (measured on the 2.9 simulator, see the server documentation).
  - `on-demand` (default) reads only while a `StreamErrors` client is connected, which is what 1.0 did.
  - `always` reads from startup, so status and late subscribers get recent messages.
  - `off` never reads and refuses `StreamErrors`.
- **`StreamErrors` sends its response headers once the subscription is in place**, so a client can tell from when it will receive messages.
- **`ToolEntry.table_index`.** Each entry of `tool.tool_table` now carries its index in LinuxCNC's own tool table. `tool.pocket_prepped` is an index into that table, and `tool_table` leaves out empty slots, so `pocket_prepped` could not be used to find the prepared tool in the list. The prepared tool is the entry whose `table_index` equals `pocket_prepped`. The list itself is unchanged.
- **`SPINDLE_CMD_CONSTANT` is implemented.** It sends LinuxCNC's `SPINDLE_CONSTANT`. It used to be answered `RCS_ERROR` ("Unknown spindle command").
- **Go: three more names in the root package.** `HalValue_PortValue`, `UnsafeLinuxCNCServiceServer` and `UnsafeHalServiceServer` are re-exported from the generated package like the rest.
- **Examples:** `mdi_command --wait-timeout` sets how long to wait for a command, `upload_file --filename` chooses the name to upload under, and the Rust examples have a README.

### Changed
- **The server starts without LinuxCNC.** It used to exit with status 1 if LinuxCNC was not running. It now starts, reports `NOT_SERVING` on the gRPC health service, answers `UNAVAILABLE` on the RPCs that need LinuxCNC, and connects when LinuxCNC comes up (it looks after 1, 2 and 4 seconds, then every 5). `UploadFile`, `ListFiles`, `ReadFile` and `DeleteFile` and the HAL service work meanwhile; `ResolveFile` needs LinuxCNC. `--require-linuxcnc` restores the old fail-fast behaviour. `LinuxCNCServiceServicer()` constructed directly still raises unless given `require_linuxcnc=False`.
- **The status lists only the machine's joints and spindles.** LinuxCNC's status always has 16 joint entries and 8 spindle entries, and the server passed them all on: a 3-joint machine with one spindle showed 16 joints and 8 spindles. `joints` now has `trajectory.joints` entries and `spindles` has `trajectory.spindles`; `limits.limit_flags` and `limits.homed` have one entry per real joint as well. If LinuxCNC reports a count that cannot be right (zero, negative or more than it lists), the full lists are sent as before. `limits.misc_error` and `axes` are unchanged.
- **The health service follows the LinuxCNC connection** instead of always reporting `SERVING`, and turns every service to `NOT_SERVING` when the server is stopped.
- **What happens when LinuxCNC stops is now documented**, as measured on the 2.9 simulator. A normal LinuxCNC shutdown stops the server, because LinuxCNC unloads the server's HAL component; run it under a supervisor such as systemd with `Restart=always` if it should come back. A crashed LinuxCNC is not detected: its status memory stays in place, so the server keeps returning the last status. Both were already true in 1.0.
- **Stopping the gRPC server also stops the server's background work.** `server.stop()` turns the health service to `NOT_SERVING`, starts the gRPC shutdown and then stops the error reader and the wait for LinuxCNC, so a stopped server no longer reads LinuxCNC's error channel and does not connect afterwards. It does not wait for a command that LinuxCNC is not answering: the gRPC shutdown and its grace period begin at once, and stopping the background work waits at most about 5 seconds. A background thread that is in the middle of a check for LinuxCNC (up to 10 seconds) or waiting behind such a command can end shortly after `stop()` has returned. It reads no more error messages and starts no connection; the only thing that can still happen is that a connection attempt already under way completes.
- **The server exits when it finds it can no longer connect to LinuxCNC.** If LinuxCNC goes away between the server's check and its connection attempt, the LinuxCNC Python module cannot connect again in the same process. The server tries 3 times in all, then logs an error, stops and exits with status 1, so a supervisor starts a fresh process. It used to keep trying and stay `NOT_SERVING` for good. Programs that call `create_server` themselves get the error log and can pass `on_unrecoverable`, a callback called once with a description (it can arrive just as the program stops the server, and should be ignored then); `serve()` raises `UnrecoverableConnectionError` after stopping the server.
- **A `create_server` that fails holds no port.** The port is now bound last, after the services are built, so a failure before that (LinuxCNC not running with `require_linuxcnc`, HAL not available, a thread that cannot start) never takes it, and the server's background threads are told to stop. The port used to be bound first and then stayed bound for the life of the process. A bad address or a port in use is therefore reported after the services were built; with `--error-channel always` the server can read an error message from LinuxCNC in that moment. The server's HAL component, if it was already created, stays until the process exits. A server that `create_server` returned but that is never started keeps its port until the process exits: gRPC's `stop()` does nothing on a server that was not started.
- **`serve()` does not wait for ever for the server to stop.** It waits 15 seconds for the stopped gRPC server (the grace period is 5), then logs an error and goes on.
- **Stream intervals are capped at 60 seconds.** An `interval_ms` above 60000 is treated as 60000 in `StreamStatus` and in the HAL service's `StreamStatus` and `WatchValues`.
- **`WatchValues` ignores duplicate names and takes at most 1000.** More than 1000 different names is `INVALID_ARGUMENT`.
- **HAL components carry only what is known.** The server infers components from pin and parameter names, because LinuxCNC's `hal` Python module has no component list. `HalComponentInfo.ready` and `type` are no longer filled in (they were always true and 1, whatever the component); `pid` and `id` remain 0. Only `name`, `pins` and `params` mean anything.
- **A pin or parameter whose direction HAL does not report is `UNSPECIFIED`.** It used to be reported as an input pin or a read-write parameter.
- **Node.js: `@grpc/grpc-js` 1.13 series, 1.13.6 or newer.** The Node.js client now depends on `@grpc/grpc-js` `~1.13.6` (it was `~1.12.0`), for the security updates in 1.12.7 and 1.13.6. A project that also lists `@grpc/grpc-js` itself should use the same 1.13 series, so that only one copy is installed. `protobufjs`, which `@grpc/grpc-js` brings in, has security updates up to 7.6.5; the client does not set its version, so update it in your own lock file (`npm update protobufjs`).
- **Go client: newer minimum dependency versions.** The Go module now requires `google.golang.org/grpc` 1.83.2 (was 1.79.3), `google.golang.org/protobuf` 1.36.11 (was 1.36.10) and, through gRPC, `golang.org/x/net` 0.58.0 (was 0.48.0), which carry the current security fixes. A project that already uses newer versions keeps them. The client's own API and the generated code are unchanged.

### Upgrade notes
- **systemd units:** use `Restart=always` rather than `Restart=on-failure`. A LinuxCNC shutdown stops the server with a normal exit.
- **Spindle and brake commands:** a client that sent a negative `speed` with `SPINDLE_CMD_FORWARD` to turn the spindle backwards (or the reverse) must send the other command with a positive speed. A client that relied on an unknown `BrakeCommand.state` value releasing the brake must send `BRAKE_RELEASE`. Both now get `RCS_ERROR`.
- **Commands with numbers that are not finite, with limits out of order, or naming a joint or spindle the machine does not have, are refused** with `RCS_ERROR` instead of being passed to LinuxCNC. A joint index must be below the machine's joint count (`trajectory.joints`), and `-1` is accepted only by `home` and `unhome`, where it means all joints. See Fixed.
- **Status lists:** a client that assumed 16 entries in `joints`, `limits.limit_flags` or `limits.homed`, or 8 in `spindles`, or that read `joints[n]` for an `n` at or above the machine's joint count, must use the lists as they come. Code that already looked only at the first `trajectory.joints` joints (and `trajectory.spindles` spindles) needs no change and works with a 1.0 server too.
- **Tool table:** `ToolEntry.table_index` is unset in a status from a 1.0 server, so check that it is present before comparing it with `pocket_prepped`; 0 is a real index.
- **Node.js/TypeScript, large 64-bit values:** a HAL `s64Value` or `u64Value` beyond 2^53 used to arrive divided by 1,000,000 and now arrives unscaled, as the nearest number. Code that multiplied such a value back must stop doing so. Timestamps are unchanged: they still arrive in milliseconds.
- **HAL values that changed meaning:** `HalPinInfo.has_writer`, `HalComponentInfo.ready` and `type`, and `HalSystemStatus.is_sim`, `is_rt`, `is_userspace`, `kernel_version` and `message_level` used to be fixed or assumed values. They are now what HAL reports, or left unset. A client that tested any of them will see different values.
- **HAL `SendCommand` with `get_value` or a `query_*` command** now returns `success = false`. Call `GetValue`, `QueryPins`, `QuerySignals`, `QueryParams` or `QueryComponents`.
- **LinuxCNC version:** the server needs LinuxCNC 2.9 or newer, because the HAL service uses functions 2.8's `hal` module does not have. This was already so in 1.0 and is now stated in the documentation.
- **Rust:** the new fields are added to the generated structs (`WaitCompleteRequest`, `CommandResponse`, `ErrorMessage`, `StreamErrorsRequest`, `ToolEntry`), so code that builds one of these messages with a struct literal needs `..Default::default()`, for example `WaitCompleteRequest { serial, timeout, ..Default::default() }`.
- **TypeScript:** two generated message types gained a required property: `ErrorMessage.sequence` and `StreamErrorsRequest.replayBuffered`. An object literal typed as one of them needs the new property, or build it with `ErrorMessage.fromPartial({...})` / `StreamErrorsRequest.fromPartial({...})`. `linuxcncSerial` on `CommandResponse` and `WaitCompleteRequest` and `tableIndex` on `ToolEntry` are optional. The generated `LinuxCNCServiceServer` and `LinuxCNCServiceClient` interfaces gained `readFile`, `resolveFile`, `getMachineConfig` and `getServerInfo`, so a hand-written implementation of either has to add them.
- **Go:** the generated `LinuxCNCServiceClient` and `LinuxCNCServiceServer` interfaces gained `ReadFile`, `ResolveFile`, `GetMachineConfig` and `GetServerInfo`. Hand-written implementations and mocks of `LinuxCNCServiceClient` must add the four methods. Server implementations already embed `UnimplementedLinuxCNCServiceServer` (the interface requires it), which supplies them.
- **Go client: Go 1.25 or later is required** (was 1.24). Every `google.golang.org/grpc` and `golang.org/x/net` release with the current security fixes needs Go 1.25, so the module's `go.mod` now says `go 1.25.0`. Updating to this release raises the `go` line of your own `go.mod` to at least 1.25.0; an older Go toolchain downloads a newer one, or stops with an error if `GOTOOLCHAIN=local` is set. A program whose `go.mod` moves from 1.24 to 1.25 also gets Go 1.25's defaults, among them a `GOMAXPROCS` that follows a container's CPU limit on Linux (see the [Go 1.25 release notes](https://go.dev/doc/go1.25)).

### Deprecated
- **`AutoCommand` and `AutoCommandType`** are marked deprecated in the proto. `SendCommand` has never been able to carry `AutoCommand`; run, pause, resume, step and abort go through `ProgramCommand`. Both stay in 1.x so existing code compiles, and will be removed in 2.0.

### Fixed
- **`WaitComplete` no longer blocks other RPCs.** It used to hold the server's global lock for the whole wait (5 s by default), so every other call, including an estop, queued behind it. It now polls status and releases the lock between polls, and its own waits for the lock end at the request's timeout: if another RPC holds the lock past the deadline, the answer is `RCS_EXEC`, as for any timeout. A wait whose client cancels ends within about a tenth of a second, also while another RPC holds the lock. It still ignores `request.serial` and waits on the latest command sent through the server, which it now picks once, when the wait starts. So a command another client sends during a wait is not followed: the wait reports `RCS_DONE` once LinuxCNC has moved past the command it started with, even if the newer one is still running. In 1.0 that could not happen, because the second command queued behind the wait.
- **`WaitComplete` follows LinuxCNC's own `wait_complete()` rule.** It returns `RCS_DONE` at once when a later command has already been echoed, and it compares serials with a signed 32-bit difference as LinuxCNC does, so the answer stays right when LinuxCNC's serial counter wraps. By a rule of the server's own it also returns `RCS_DONE` at once when nothing has been sent through the server since it connected. It keeps working if the server reconnects to LinuxCNC during the wait.
- **`WaitComplete` after a command that failed part-way.** If a command made of several LinuxCNC messages (`coolant`, `set_limit`, `override_config`, `program_options`) fails after the first message went out, `WaitComplete` now waits on that message instead of reporting on the previous command. This needs LinuxCNC bindings that expose `command.serial` (2.8, 2.9 and master do); without it the server cannot tell that part of the command went out, and `WaitComplete` reports on the previous command as before.
- **`SendCommand` no longer sends a command it cannot track.** This only concerns LinuxCNC bindings without `command.serial` (2.8, 2.9 and master have it). There the server polls status before each command to have a baseline for `WaitComplete`; if that poll fails, `SendCommand` now answers `RCS_ERROR` and sends nothing. It used to ignore the failure and send the command.
- **`scripts/wait-for-linuxcnc.py` could wait forever.** If its first attempt came before LinuxCNC was up, no later attempt in the same process could succeed. Each attempt now runs in its own process. `--timeout` is a deadline for the whole run: the first check (that the `linuxcnc` module can be imported), every attempt and every pause between attempts stop at it.
- **A failed reconnect no longer leaves the server half-connected.** The status, command and error channels are replaced together, and only once the new connection has answered a poll.
- **Uploads are put in place in one step.** `UploadFile` writes the content to a temporary file in the destination's directory (`.linuxcnc-grpc-upload-<random>.tmp`, which `ListFiles` does not show) and gives it the destination's name once it is complete. A reader never sees part of an upload, and an upload that fails (a full disk, for example) leaves the previous file untouched; it used to leave a truncated file. The publish step does not follow a symbolic link put at the destination after the name was checked. Replacing a file now puts a new file under the name: it keeps the old file's permission bits, but another hard link to the old file keeps the old content. A file the server cannot write is still not replaced.
- **`UploadFile` with `fail_if_exists` is safe against concurrent uploads.** The finished file gets its name only if the name is still free, so of two uploads of the same new name only one succeeds and the other gets `ALREADY_EXISTS`. Both could succeed before, the second overwriting the first. A failed upload leaves no file behind, so a retry is not answered `ALREADY_EXISTS`, and it never removes a file another request created under that name meanwhile. This needs a file system with hard links; where there are none (some network and FAT mounts) an upload with `fail_if_exists` fails with `INTERNAL` and writes nothing.
- **A symbolic link loop in a file name is `INVALID_ARGUMENT` on every Python version.** The answer used to depend on the Python version (`UNKNOWN` on 3.12 and older). A loop in the NC files directory itself is `INTERNAL` from `ListFiles`, `ResolveFile` and `GetMachineConfig` on every Python version (it escaped as `UNKNOWN` on 3.12 and older, and went unnoticed on newer ones), and `ResolveFile` reports a loaded program whose path cannot be resolved as not loaded.
- **The server's own response serial wraps.** The counter behind `CommandResponse.serial` (used when the request's serial is 0), and the one in the HAL service, went on past the int32 range, where building the response failed. Both now wrap to 1 after 2147483647.
- **A command is not sent once the server is stopping or its client has gone.** `SendCommand` handles one command at a time, and a command could wait behind another for seconds. It was then still sent to LinuxCNC after the server had begun to stop or after its own request was cancelled. It is now answered `RCS_ERROR` and nothing is sent. Commands that only stop things are the exception and are always sent: E-stop, machine off, program abort and pause, jog stop and spindle off.
- **A failure during startup or shutdown is not hidden by a second one.** If cleaning up after a failed start fails too, the cleanup failure is logged and the caller of `create_server` or `serve()` gets the original error. Stopping the server runs every step and then raises the first failure.
- **`serve()` restores the previous `SIGINT` and `SIGTERM` handlers** when it returns or fails. It used to leave its own handlers installed. Where the previous handler was not set from Python and cannot be put back, it restores the default action. It installs its handlers before it creates the server, so a signal during startup stops the server normally.
- **The `UploadFile` size error says characters.** The limit counts characters; the message said bytes.
- **Spindle off, increase and decrease act on the requested spindle.** They always acted on spindle 0, whatever `spindle` said.
- **A negative spindle speed is rejected for forward and reverse.** LinuxCNC multiplies the speed by the direction, so a negative speed turned the spindle the opposite way to the command.
- **An unknown brake state is rejected.** Any value other than `BRAKE_ENGAGE` used to release the brake.
- **Commands carrying NaN or infinite numbers are rejected** with `RCS_ERROR`, and nothing is sent to LinuxCNC. This covers the jog velocity and increment, the spindle speed, the feed, rapid and spindle override scales, the maximum velocity, the tool offset values, the analog output value and the joint limits. The override scales and the maximum velocity must also be zero or more. Only the fields an operation uses are checked, so a jog stop or a spindle stop is never refused over them.
- **`set_limit` needs `min_limit` below `max_limit`** and sends neither limit otherwise. It used to send both as given.
- **`set_limit` and `override_config` check their joint and spindle index before sending anything.** `override_config` with a spindle that does not exist used to send the feed override setting and then pass the bad spindle number on; `set_limit` sent both limits for any joint number, negative ones included. Both now answer `RCS_ERROR` and send nothing.
- **Joint indices are checked against the machine's joint count.** LinuxCNC's status always lists 16 joints, and the server accepted any index below 16 for a joint jog, `home` and `unhome`. An index at or above `trajectory.joints` is now `RCS_ERROR`, as is a joint jog with index `-1`; `-1` still means all joints for `home` and `unhome`. Spindle indices are checked the same way: LinuxCNC's status always lists 8 spindles, and an index at or above the machine's spindle count is now `RCS_ERROR`.
- **Spindle forward and reverse work on LinuxCNC 2.8's bindings** when `wait_for_at_speed` is false. The server always passed a fourth argument that 2.8 does not accept.
- **`limits.misc_error` carries LinuxCNC's values.** It was a list of zeros, one per joint. Its length is now that of LinuxCNC's own array.
- **The LinuxCNC service handles LinuxCNC 2.8's status.** `GetStatus`, `StreamStatus` and `GetMachineConfig` failed there on attributes 2.8 does not have. Those fields are now reported as defaults, and `motion_id` is read from 2.8's `id`. (The server as shipped still needs 2.9 for the HAL service; this helps a server built from `LinuxCNCServiceServicer` alone.)
- **Streams stop waiting when the client goes away.** `StreamStatus` and the HAL streams slept through their whole interval after the client had cancelled or disconnected, holding a server thread; ten calls with a very long interval blocked every RPC. The wait now ends at once, and at server shutdown.
- **`WaitComplete` with a very large or infinite timeout waits** instead of failing with `UNKNOWN`. A NaN timeout means the default.
- **An unexpected error while reading LinuxCNC's status is no longer `UNKNOWN`.** A status poll can fail with something other than LinuxCNC's own error (on some LinuxCNC builds a failed poll surfaces as Python's `SystemError`, "error return without exception set"). `GetStatus`, `StreamStatus`, `ResolveFile` and `GetMachineConfig` now answer `INTERNAL` with the error's type and text, and `WaitComplete` answers `RCS_ERROR` with the same text, as `SendCommand` already did. The other status codes of these RPCs are unchanged.
- **`GetMachineConfig` counts joints and spindles the way the status does.** With a joint count from LinuxCNC that cannot be right (zero, negative, more than it lists, or missing) it listed no joints or failed, where `GetStatus` sends the full list. `joint_count`, `joints` and `spindle_count` now always agree with the joints and spindles `GetStatus` lists.
- **Node.js/TypeScript: 64-bit values beyond 2^53 are no longer divided by 1,000,000.** The generated decoder scaled every 64-bit integer beyond 2^53 down by a million. That was meant for nanosecond timestamps, but it also changed a large HAL `s64_value` or `u64_value` (and any other large 64-bit field). Only timestamps are scaled now. Other 64-bit fields are still JavaScript numbers, so beyond 2^53 they arrive as the nearest number and lose their low digits; exact values would need a different TypeScript type, which is a change for 2.0.
- **HAL: unsigned values above 2147483647 no longer break `QueryParams`, `GetValue` and `GetSystemStatus`.** One such parameter made the whole call fail. On LinuxCNC 2.9, which lists no type for parameters, an unsigned parameter at or below that value is still reported as `HAL_S32`.
- **HAL: one item that cannot be mapped no longer fails a whole listing.** It is left out and logged. That holds for `GetSystemStatus`, the status stream, `QueryComponents` and `QueryPins`, `QuerySignals` and `QueryParams` with a pattern, also when the item has no usable name (a name that is not text).
- **`WatchValues` ends when a watched name can no longer be read.** After five polls in a row with a failed read it ends with `INTERNAL` and names an item that failed; it used to go on without reporting anything. It no longer reports an unchanged NaN as a change on every poll.
- **`HalPinInfo.has_writer` is HAL's own answer.** It was true for every output pin and false for every other pin.
- **HAL port pins have no value.** They were reported with a value of 0. Their type is `HAL_PORT` where LinuxCNC reports the type.
- **HAL `SendCommand` no longer reports success for commands it cannot answer.** `get_value` and the `query_*` commands returned `success = true` and no result; they now return `success = false` and name the RPC to call.
- **`is_sim`, `is_rt`, `is_userspace`, `kernel_version` and `message_level` are read from HAL.** They were fixed values (not a simulation, real-time, `MSG_INFO`).
- **A HAL status stream that fails reports the cause.** After five failed polls it ends with `INTERNAL` and the last error.
- **Examples: `jog_axis` always sends the jog stop**, also on Ctrl+C, on SIGTERM and after an error, and sends it before printing anything. The Python example's signal handler no longer takes a lock.
- **Examples: `jog_axis` and `mdi_command` no longer reset E-stop or power the machine on.** They require a machine that is on and homed and stop with a message otherwise. Mode and teleop changes are waited for and checked in the status instead of sleeping.
- **Examples: jog velocities are in machine units per second.** The old examples used 100 and 50 and labelled them units per minute. On the 2.9 simulator a jog at velocity 1 moved 0.53 units in 0.5 seconds. The examples now use 1.
- **Examples: `mdi_command` waits on the command's `linuxcnc_serial`** and reports a timeout as a timeout, not as completion. `RCS_DONE` from that wait also comes back when LinuxCNC has taken a later command from any client (a feed override changed in the GUI, for example) while the MDI move is still running, so the example then reads the status until the machine is idle (interpreter idle, `trajectory.inpos` true, velocity zero), within what is left of `--wait-timeout`, and prints `Done.` only then; otherwise it reports the result as not confirmed and exits non-zero. If the machine is no longer on (an E-stop from another client also ends the wait with `RCS_DONE`), it reports that the command was stopped and exits non-zero. It cannot tell an abort from another client from completion: the machine is then on and idle as after a finished move. In interactive mode it exits non-zero if any command failed. Ctrl+C ends the example at once, also in the middle of a wait, and sends no abort to the machine.
- **Examples: `upload_file` does not overwrite an existing file**, and `--cleanup` deletes only the file that run uploaded.
- **Examples: `hal_query` exits non-zero on failure** and no longer prints component columns the server does not fill in. The Rust `get_status` prints the exec and interpreter states by name, as the other three do. Every unary RPC in the examples has a deadline; the streams run until interrupted.
- **Examples: the Go README commands dropped `--`.** `go run ./cmd/x -- --flag` made Go's flag parser ignore every flag after the `--`.
- **Examples: `mdi_command` and `jog_axis` check that the machine is idle before every command or jog**, also when the machine is already in the right mode, so a command is not sent on top of one that is still running. Idle means the interpreter is idle, `trajectory.inpos` is true and `trajectory.current_vel` is zero; the interpreter state alone does not show a running MDI move reliably. `jog_axis` makes its checks (machine on, homed, idle) on a fresh status right before each jog is started, so a machine put in E-stop, turned off or given a program between two jogs gets no further jog; a jog stop is never held back by them. While it waits for an axis to stop it also watches the machine state, and ends with the "machine is not on" message as soon as the machine is in E-stop or off. `--wait-timeout` must be greater than 0 and at most 86400 seconds and is checked before anything is sent.
- **Examples: `stream_status` and `hal_query watch` exit non-zero when the server cancels the stream** (Python and Node exited 0). The `stream_status` idle timeout is the larger of 30 seconds and twice `--interval` plus 5 seconds, and `--interval` must be 1 to 60000. The Rust `stream_status` no longer hangs when the server accepts the connection but never answers.
- **Examples: a jog stop that fails exits 1 in all four languages**, also after Ctrl+C, and is reported before a panic resumes in Go and Rust. The Go `mdi_command` reports an input read error instead of treating it as the end of input.
- **Uploads just over the cap get a clear error.** `UploadFile` refuses content longer than 10 MiB (10,485,760 characters) with `INVALID_ARGUMENT`, but the gRPC receive limit was 10 MiB too, so the transport rejected such a request with `RESOURCE_EXHAUSTED` first. The receive limit is now 11 MiB. A request larger than that (possible below the character cap with non-ASCII text, which takes more than one byte per character) still gets `RESOURCE_EXHAUSTED`.

### Documentation
- **New page: Using with Claude (MCP).** It introduces [linuxcnc-mcp](https://github.com/dougcalobrisi/linuxcnc-mcp), an MCP server and Claude Code plugin built on this API, and describes how it uses the API.
- **Security warning.** The README and the server page now say plainly that the server has no authentication and no TLS, and show how to bind to `127.0.0.1` and connect through an SSH tunnel.
- **Command semantics.** `RCS_DONE` from `SendCommand` means the command was dispatched, not that it finished. `CommandResponse.serial` is the server's own serial, not LinuxCNC's, and must not be compared with `echo_serial_number`. The `WaitComplete` rules are written out.
- **Mode and teleop sequencing.** The API reference now says which task mode and teleop state each command needs, what LinuxCNC answers in the wrong state, how refused jogs and homes show up (still `RCS_DONE`), and why `inpos` cannot be used to wait for an axis jog. Measured on the LinuxCNC 2.9 simulator.
- **Telling whether the machine is idle.** The API reference now says, as measured on the 2.9 simulator, that `task.interp_state` alone is not a reliable busy test for MDI (it read `INTERP_IDLE` for the whole of 7 of 71 MDI moves) and that it should be used together with `trajectory.inpos` and `trajectory.current_vel`; and that `trajectory.current_vel` keeps its last value after an E-stop until the machine is turned on again.
- **Error delivery.** How error messages reach clients, and why reading them takes them from the machine's GUI.
- **The examples guide matches the example code again**, and the package docstring's `serve()` example runs as written.
- **API reference:** how many joints and spindles the status lists, how to find the prepared tool, that a tool table entry can have id -1 (an empty slot, such as the spindle with no tool loaded) and should be ignored unless its id is positive, how 64-bit integers arrive in Node.js, the command value checks, the spindle commands, the HAL fields the server does and does not fill in, HAL `SendCommand`, the `WatchValues` limits and error codes, and the stream interval cap.
- **Requirements:** the server page and the setup page say LinuxCNC 2.9 or newer.

### Maintainer tooling
These do not affect users of the packages.
- **Publishing:** `publish-node.sh` applies the npm dist-tag of a pre-release and refuses a pre-release it cannot derive a tag for; the artifact version checks match the version exactly; `publish-all.sh` refuses a tree with uncommitted changes unless given `--allow-dirty`, creates the tag only after every package was published, and checks an existing local or remote tag first.
- **`sync-versions.sh`** reports a lock file it could not update and stops before any commit, changes only the project's own entry in `uv.lock`, also sets the versions of the example projects, and refuses `--tag` without `--commit`.
- **Release workflow:** it checks the tag on the remote before publishing, runs one release at a time, and fails if a registry already has the version. Only a run started with the input `resume_partial_release` set to true (default false) skips a version that is already published; that input is for running a release that failed part-way again on the same commit.
- **Mock server (`tests/mock_server.py`):** it now refuses what the real server refuses, with the same messages: joint and spindle indices the mock machine does not have, axis indices outside LinuxCNC's nine axis slots (0 to 8), non-finite analog output and tool offset values, unknown spindle command and jog type values, and `WatchValues` with no names, more than 1000, or a name it does not know. Its `WatchValues` also sends a batch only when a value changed, as the real one does; the mock's values never change, so it no longer sends an empty batch every interval.
- **Proto generation:** the step that patches the generated TypeScript stops with an error if it does not recognise the code it is meant to patch. It used to do nothing in that case.
- **CI:** GitHub Actions in the workflows are pinned to commit SHAs (each at its latest release, which moved checkout, cache, setup-go, setup-node, upload-pages-artifact, setup-uv and action-gh-release up a major version), and Dependabot keeps the pins current. Hugo, the docs theme, uv, the protoc plugins and the LinuxCNC source used by the e2e job are pinned too. The release job installed `npm@latest`, which no longer runs on the Node version the job uses; it now installs a fixed npm 11. The e2e job fails if no test passed or a test was skipped unexpectedly; the stream examples must still be streaming when their timeout stops them, where every exit status used to be ignored; the protoc download is verified against a SHA-256; workflow permissions are narrowed to what each job needs. The e2e job's LinuxCNC build cache is keyed by the pinned commit and the checkout is verified on every run. A release dry run now works for a version that is already on npm and for a pre-release.
